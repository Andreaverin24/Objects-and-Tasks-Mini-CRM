# Объекты и задачи

Демонстрационная CRM для строительной компании. Постановщик создаёт объекты и назначает задачи. Исполнитель работает со своими задачами и отправляет результат на проверку. Приложение использует React, TypeScript, Vite и Supabase.

## Запуск

1. Создайте отдельный проект Supabase. В настройках Auth отключите регистрацию новых пользователей и оставьте вход по email и паролю.
2. Выполните миграцию [CRM](supabase/migrations/20261108000100_crm.sql) в SQL Editor.
3. В Authentication → Users создайте три подтверждённых аккаунта. Назначьте каждому уникальный пароль.
   - Постановщик — `manager@crm-demo.example.com`
   - Исполнитель А — `worker-a@crm-demo.example.com`
   - Исполнитель Б — `worker-b@crm-demo.example.com`
4. Выполните [скрипт демонстрационных данных](supabase/demo-data.sql) один раз. Он привязывает роли к пользователям и добавляет два объекта с задачами в разных статусах.
5. Скопируйте `.env.example` в `.env.local` и укажите URL проекта и ключ Supabase Publishable. Для Vercel задайте эти же переменные в настройках окружения проекта.
6. Установите зависимости через `npm ci` и запустите `npm run dev`. Для сборки используйте `npm run build`.

В репозитории хранятся миграции и шаблон окружения. Пароли демо передаются отдельно. Ключ `service_role` приложению не нужен.

## Объяснение для руководителя

В CRM у каждого строительного объекта есть список задач. Постановщик назначает исполнителя и проверяет результат. Исполнитель видит свои задачи и объекты, к которым они относятся. После выполнения он отправляет задачу на проверку. Постановщик может принять её или вернуть с объяснением. В карточке видно, кто и когда менял статус, и можно прочитать комментарии.

Правила доступа проверяет сама база данных. Даже если исполнитель попробует обратиться к базе в обход сайта, ему будут доступны только его задачи. Он не сможет переназначить задачу, пропустить этап проверки или изменить историю. При смене статуса база одновременно добавляет запись в историю и сохраняет в ней автора и время.

## Решения и допущения

- Все постановщики видят все активные объекты и задачи. Исполнитель видит объект, пока у него на нём есть хотя бы одна активная задача. Принятая задача остаётся доступной до архивирования.
- Удаление в интерфейсе архивирует объект или задачу. При удалении объекта его задачи исчезают из рабочих списков, а их история сохраняется в базе.
- При переназначении доступ переходит новому исполнителю, включая историю этой задачи. Автор и время создания сохраняются. Задачу можно перенести на другой активный объект.
- История содержит первоначальное создание и последующие изменения статуса. Обычное редактирование описания или исполнителя не меняет статус. Принятие завершает цикл.
- Пользователей и роли заводит администратор проекта. Для демо используются вымышленные данные.

## Проверка

`npm run test:db` прогоняет миграцию в PostgreSQL (PGlite). Тесты используют модель ролей и `auth.uid()` Supabase для проверки политик RLS и запросов от разных пользователей. Они покрывают цикл задачи с возвратом, изоляцию двух исполнителей, попытки поменять роль или статус напрямую, подделать историю и обратиться без входа. На развёрнутом демо стоит отдельно пройти вход тремя аккаунтами и повторить запрещённые запросы с их сессиями через Data API.
